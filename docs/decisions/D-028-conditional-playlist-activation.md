# D-028 — Conditional playlist activation and external conditions

- **Status:** Accepted architectural direction
- **Date:** 2026-10-15
- **Decision:** Allow playlist assignments and playlist selection to be gated by server-evaluated conditions, including the state of an external service (for example, whether a YouTube Live stream is active) or values extracted from an external HTTP API's JSON response (for example, a URL field).
- **Dependency:** Use `varfetch` as the planned server-side HTTP connector dependency (`varfetch@^0.3.0` at the time of this decision). The repository is currently a documentation-first plan and has no application `package.json`; add the dependency to the server application's manifest when that application is scaffolded. Do not create a misleading root manifest just to declare a future dependency.
- **Evaluation boundary:** Evaluate conditions on the SiSSi server, not in scene JavaScript or signage clients. External credentials and connector configuration stay server-side. Clients receive only the resulting desired playlist/configuration, never API secrets or arbitrary connector definitions.
- **Condition model:** A condition has a stable ID, enabled state, connector/request reference, response mapping, predicate/operator, expected value where applicable, evaluation cadence or cache lifetime, timeout, and explicit unknown/error policy. Conditions may be composed with documented AND/OR groups. Initial examples include a boolean-like livestream-active signal and a JSON field whose value is compared or used as a validated URL.
- **Separation of concerns:** Keep external condition evaluation distinct from playlist content, scene time guards, and calendar schedules. A condition may determine whether a playlist assignment is eligible, or which playlist is selected; it must not mutate the playlist or a published scene revision.
- **Freshness and failure handling:** Track last successful evaluation time, result, and error status. Define stale-result limits and explicit behavior for timeout, malformed responses, missing JSON paths, rate limiting, and service outages. Never silently treat an unknown/error result as false or true; the policy must be selected explicitly for each assignment, with a safe tenant-configurable fallback.
- **Security:** Apply varfetch's SSRF protections. Private/internal network access must be denied by default and permitted only by trusted server-side allow rules. Users must not be able to configure a condition that turns SiSSi into an unrestricted HTTP proxy. Validate schemes, hosts, redirects, response size/type, JSON mappings, URL values, and credentials. Do not allow arbitrary response-derived URLs to be fetched or displayed without policy validation.
- **Audit and operations:** Record condition configuration changes and evaluation outcomes sufficiently for operators to diagnose why a playlist was or was not selected, while redacting secrets and sensitive response content. Provide a manual test action and visible last-checked/result/error state.
- **References:** [Content and playback model](../content-model.md) · [varfetch](https://github.com/jsilvanus/varfetch) · [varfetch security model](https://github.com/jsilvanus/varfetch/blob/main/docs/security.md)

This decision records the intended design. Runtime schemas, supported predicates, polling limits, provider-specific YouTube Live checks, UI, and automated tests remain to be specified and implemented.
