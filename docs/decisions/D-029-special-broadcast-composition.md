# D-029 — Special broadcasts and multi-region display composition

- **Status:** Accepted architectural direction
- **Date:** 2026-10-15
- **Decision:** Support a temporary **special broadcast** that can be activated alongside the normal playlist on a display or screen group. The normal playlist remains the base programme while a second, independently configured playlist is presented simultaneously in a separate region, such as picture-in-picture (PiP), left/right split, top/bottom split, or another supported layout.
- **Use cases:** A church service livestream can appear in a PiP window or one half of the display while the usual notices and announcements continue in the remaining region. Special broadcasts can be started manually or activated by a conditional rule such as a live-stream/API condition.
- **Composition model:** Model this as a display composition/overlay assignment, not as an ordinary playlist item inserted into the base playlist. A composition has a base playlist assignment, one or more concurrent secondary playlist assignments, a layout preset, region geometry/order, activation conditions, priority, and explicit start/stop/expiry behavior. Initially, one secondary broadcast is sufficient; the model should not preclude more regions later.
- **Independence:** Base and secondary playlists retain their own ordered items and playback policies. The secondary layer must not advance, replace, or mutate the base playlist. On activation, prepare and validate the secondary content before displaying it; on deactivation, remove the secondary region and restore the base layout without resetting the base playlist position.
- **Target capability:** PiP and split-screen are SiSSi composition features, not assumptions about hardware TV PiP support. The client compositor must support the selected layout and multiple concurrent playback surfaces. Define capability negotiation, supported media combinations, audio focus/mixing, scaling/cropping, accessibility, and performance limits. If a device cannot support the requested composition, apply an explicitly configured fallback (e.g. switch to full-screen broadcast or keep the base playlist) and report the result; never silently claim PiP succeeded.
- **Layout and interaction:** Provide initial presets for full-screen base, corner PiP, vertical split, and horizontal split. Keep safe margins and per-region fit rules. Define whether secondary content is muted or owns audio by default; do not allow two audible streams accidentally. Display clients receive only the resolved authorized composition and content references, not connector credentials.
- **Publishing and operations:** Special-broadcast activation/deactivation is a permissioned action, auditable and visible in status. Support targeting an individual display or screen group, preview/test, scheduled expiry, manual stop, condition-based activation, and deterministic conflict/priority rules when multiple special broadcasts target the same display.
- **Relationship to conditional activation:** Conditions can decide whether a special broadcast is active. Condition evaluation is server-side (see [D-028](D-028-conditional-playlist-activation.md)); display clients execute the resulting composition. Conditional activation and visual composition remain separate concerns.
- **References:** [Content and playback model](../content-model.md) · [Conditional playlist activation](D-028-conditional-playlist-activation.md)

This decision records the intended behavior, not an implemented feature. Exact schemas, layout geometry, compositor API, audio policy, device capability contract, and test matrix remain to be specified.
