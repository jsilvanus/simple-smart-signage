# D-044 — Complex-scene security model

- **Status:** Accepted architectural direction
- **Date:** 2026-10-16
- **Scope:** AI- or user-authored HTML/CSS/JavaScript scenes running in the SiSSi display runtime.
- **Decision:** Use layered, policy-controlled isolation for authored scenes. Scenes run in sandboxed iframes and receive only explicitly permitted capabilities. The scene manifest declares requested capabilities; tenant policy defines the maximum; sensitive grants may require approval; the trusted runtime computes and enforces effective permissions. Scenes cannot grant permissions to themselves, and changes to requested capabilities trigger re-evaluation. Network access is hybrid: explicitly approved public/browser-accessible requests may be direct, while privileged or credentialed requests go through server-side SiSSi connectors. Credentials remain server-side. Resource budgets are profile-based and adapted to device capability, with runtime monitoring, bounded operations and host-controlled recovery; there is no blanket maximum playback lifetime for a valid continuous scene. Trust and publication review is risk-based, with stricter validation/approval for custom executable code and sensitive capabilities, and approval bound to a specific published revision and its requested capabilities. Browser/device APIs use an explicit per-capability allowlist, with sensitive APIs denied by default and exceptions subject to policy/approval. Security is defense in depth: browser controls constrain execution, the trusted player validates scene identity/revision and bridge messages and controls privileged display actions, and the server enforces tenant authorization, connector security and publication policy. For the MVP, violation handling is limited to denying an operation and continuing, or terminating the scene; severity-based escalation is planned for 2.0. Serious isolation or privilege-boundary violations must fail closed.
- **Origin and iframe isolation decision:** Serve scene documents from the SiSSi server, but load them in a sandboxed iframe without `allow-same-origin`, giving the document an opaque origin. This is the preferred MVP design, conditional on security validation on every supported browser/WebView. Do not grant `allow-same-origin` to untrusted authored scenes as a convenience workaround. The scene document must not receive application session cookies or gain access to privileged application state/endpoints. The host must treat messages from an opaque origin carefully: do not authorize based on a claimed origin or scene-supplied identity; validate the actual iframe/window relationship, active scene instance, revision, message schema, allowed operation and server-side authorization. If required features or platform behavior prevent the isolation from being demonstrated, use a dedicated scene origin with no application session cookies. Do not ship untrusted scene execution until one of these isolation strategies passes the security gate.
- **MVP implementation baseline:** Prioritize browser sandboxing, restrictive CSP and capability restrictions; host-validated bridge messages; server-side authorization for privileged operations; and basic deny/terminate handling. Start from a minimal iframe sandbox grant (scripts only where required) and add capabilities only for documented product needs. Do not grant top navigation, popups, downloads, modal dialogs, pointer lock, camera/microphone, geolocation or other sensitive APIs by default. Define CSP `default-src` and resource-specific directives explicitly rather than relying on browser defaults; direct network destinations must be limited to approved public resources, and connector traffic must be server-authorized. These are baseline requirements to refine against actual browser/WebView support, not a finalized list of exact directives. Structure the design so runtime monitoring/recovery and richer server/runtime defenses can be strengthened without changing the scene trust model.
- **Rationale:** AI-authored executable scenes must remain useful for signage while being unable to self-authorize, access server secrets, bypass tenant policy, or compromise the trusted player. No single layer can reliably enforce every boundary across browser, device and server environments.
- **Open implementation details:** Exact iframe sandbox flags and CSP directives; browser/WebView test evidence that the opaque-origin approach works for required scene features; cookie/session and scene-document authentication behavior; capability registry and profile definitions; tenant approval roles and revision invalidation; direct-request destination rules and redirect/DNS/IP validation for connectors; per-profile CPU/memory/network/message budgets and monitoring APIs across Android/Tizen; scene termination and last-good-frame behavior; event schema, severity thresholds, audit retention and admin controls; security test plan for each supported browser/WebView.
